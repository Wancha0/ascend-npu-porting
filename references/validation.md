# 模型验收

## 推理

记录完整 checkpoint 身份、实际入口、精度、输入及输出形状。严格加载后执行真实输入；验证转换前输出有限性、解码结果、帧数/分辨率或任务对应内容。保存模型可读的原始指标和人工可查看的输出。没有对应基准时不宣称数值或任务效果与 CUDA 等价。

## 真实训练最小闭环

从生产 dataloader 或与其契约一致的真实缓存进入 loss → backward → 梯度同步 → optimizer → 保存。用户只要求可行性时可以限定 1 次成功更新，但不能用 toy 模型、随机输入替代真实任务。

每个 rank 至少保留：

- rank/local_rank/world_size、hostname、PID、物理可见卡与实际 device、通信 backend；
- 源码 revision/差异、模型路径身份、冻结/训练模块和 wrapper；hash 按本轮契约提供；
- 数据项总数/不同真实样本数/重复次数、实际消费的样本 ID、batch 与累积；
- loss 及有限性、梯度有限性/范数/非零参数数量、同步方式；
- optimizer 更新前后计数、是否 AMP 跳步、选定参数更新前后差异、optimizer state 的步数与有限性；
- 训练命令实测退出码、结束时间、残留进程和资源释放检查。

每卡 batch 为 B、rank 数为 W、累积为 A 时，完整累积窗口名义 batch 是 `B×W×A`；还要核实最后一个窗口、sampler 补齐/重复和实际消费。两个样本重复四次分给 8 rank，不得写成八个不同样本。

检查参数变化时选择确实收到非零梯度的可训练参数，保存完整参数名、测量方法和变化量。BF16 下更新可能小于参数舍入间隔，不能凭 optimizer 调用次数认定变化；也不要任意调大学习率来通过断言。明确报告是抽检参数还是全部参数验证。

### 框架下的真实更新测量

- 参数名称来自实际 `named_parameters()`。共享模块或重复引用可能被去重，不能从 checkpoint 前缀或模块别名猜测采样名称；先确认选中数量不为零，覆盖本任务实际训练的主要分支。
- 依据目标已安装框架源码确定真正更新时点。某些 Accelerate/DeepSpeed 组合在 `accelerator.backward()` 内执行 engine 的更新，外层 `optimizer.step()` 只是包装接口。更新前参数快照及 engine/optimizer 计数应取在**第一个可能触发更新的调用之前**；快照必须 `detach().clone()`，不能共享原存储。
- 分片优化器可能把梯度转移到内部缓冲，更新后也可能清空 `.grad`。`.grad is None` 不能单独推出该分支没有梯度。必要时在 backward 前为少量已选参数注册 tensor hook，保存有限性、非零数及范数，结束后移除；标明这是本地 autograd 梯度，不能当作同步后梯度。需要同步证据时使用该框架支持的接口/缓冲读取方式。
- 更新后的参数差值应在实际更新和所需同步完成后读取。统计非零变化数、最大绝对差和范数；记录 AMP 跳步与实际计数变化。单独的 loss、梯度范数或成功 step 日志不能代替参数变化。
- 若训练已经结束而采样器写错，可用保存权重与准确的初始化参考作后验比较。参考必须经过与实际加载相同的 key 转换、dtype 转换及其他初始化变换；记录比较位置和范围。原始 FP32 权重与训练 BF16 权重直接相减，会把加载舍入误认为更新。随机初始化模块没有准确初始快照时不可用此法证明它的更新。

框架源码入口见 [官方资料索引](official-links.md)。不要只为了审计改训练算法、优化器或学习率；证据不足先修测量方法，再决定是否真的需要重跑。

真实训练“已更新”与“全生命周期验收通过”可以分开记录。即使 SSH 丢失退出码，更新证据仍应保留；不能由它补造成功退出。

## 保存与恢复

权重文件出现只是保存产物，文件大小不能证明内部状态完整。

在新进程中检查并恢复：模型 keys/shapes/dtypes、optimizer state、scheduler、更新计数、RNG、数据顺序及进度；在相同拓扑和契约下再完成有效更新。必要时对照不中断的短训练分支，在明确容差内比较。

数据恢复按**已经消费**的 batch/sample 进度，不用迭代器因预取而提前拉取的位置。若恢复时已达到最大更新数，应直接停止，不得再多更新一次。不同 rank 的 RNG/采样状态也要分别处理。共享的单文件报告可由 rank 0 写；分布式 checkpoint 按框架规定让所有所需 rank 参与保存/恢复及分片写入，不能把整个 collective 保存入口包进 rank-0-only 条件。

若恢复不是用户当前目标，写 `not_tested` 并先交付已完成的可行性结果，不为补齐所有层级拖延本轮。

## 证据文件约定

推荐结构是建议，不要求模型为符合格式重跑已经成功的训练：

```text
run-唯一编号/
  contract.json             # 冻结的本次契约
  ledger.md                 # 当前结论、最新动作、下一步
  attempt-001/
    command.sh              # 无凭证的具体入口
    runner.json             # 启动身份
    output.log              # 本任务原始输出
    result.json             # 实测退出码；未知用 null
    rank-0-step-1.json       # 其余 rank 同样保留
    artifacts.json          # 产物路径、大小、用途；哈希按契约选用
```

区分字段：`training_exit_code`、`ssh_exit_code`、`validation_exit_code`，不以最后一条 `echo`、`tee` 或验证命令退出 0 替代训练退出码。`pass` 必须对应明确检查及原始证据；未知、未测、失败不能混入总体通过。

若验证器失败，先检查它是否理解当前实际 schema：例如 `DistributedType.MULTI_NPU` 的枚举字符串、13 个 shard 的真实路径、JSON 根类型。原始产物正确而验证器预期错误时，仅修验证器并重新读已有产物，无需重跑昂贵训练。

需要内容清单时使用稳定的相对路径及约定的摘要。`.git`、`__pycache__`、`*.pyc` 和 macOS `._*` 包装文件可以按明确规则排除；不要按残留文件总数反复阻断，也不要排除模型源文件去掩盖不一致。用户要求 no-hash 时遵循[快速训练策略](fast-training.md)，不得为了这一建议延迟训练。

## 已知历史案例的结论边界

ActionWM 的开发轮验证了完整 MiniMax-H3 视频 DiT 冻结、发布版 ControlNet 训练、真实缓存、单节点 8 NPU 的一次更新。采用 BF16、CPU 模型/optimizer offload、显式 HCCL 平均。该轮没有证明全参数微调、长期收敛、新进程恢复、任意累积数或 FastWAM；SSH 中断还留下退出码缺口。

这些事实用于解释验收边界和改进操作方法。新模型需要自己的数据与参数更新证据，不使用历史数值作为应当匹配的断言。

FastWAM 的真实前向算子覆盖、参数测量和资产准备经验见 [FastWAM 附录](fastwam-lessons.md)。
